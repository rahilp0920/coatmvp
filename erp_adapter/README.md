# ERP Adapter MVP — agent-ready, self-learning ERP via MCP

A working prototype of the pitch:

> ERP is the backbone of every enterprise, yet it remains unusable by AI. We
> sit atop existing ERPs, learn from real workflows, and generate
> company-specific context, permissions, and agent-ready interfaces — all
> exposed via MCP.

The MVP focuses on **inventory** and **transaction** management and demonstrates
the three claims that matter:

1. **"Every ERP is different."** A deliberately messy mock ERP with cryptic
   column names (MATNR, BUKRS, BWART), custom Z-tables, and stock split across
   three tables.
2. **"It learns where information is stored."** A discovery layer introspects
   the schema and asks Claude to map physical tables/columns to business
   concepts (`item`, `stock_by_warehouse`, `available_stock`, …). Falls back
   to a curated mapping offline.
3. **"Agents act safely."** Claude drives the ERP via a small set of
   high-level MCP tools. A live workflow learner mines every tool call and
   refines per-company routing/approval patterns the agent then consults.

## Quick start

```bash
pip install -r requirements.txt

# One-shot: build DB, discover schema, mine patterns, run scripted demo

# To run the *live* Claude agent (requires ANTHROPIC_API_KEY):
export ANTHROPIC_API_KEY=...

# To inspect what the system has learned:
```

### The "where is information stored" problem

`get_stock(matnr)` looks like a single tool call to the agent. Internally the
adapter:

1. Reads `WH_STOCK` to get plant-level rollups (`LABST` = unrestricted).
2. Reads `BIN_DETAIL` for the bin-by-bin breakdown — the source of truth.
3. Subtracts active rows from `Z_RESERVED` (custom table, not a foreign-key
   relationship anywhere) to compute *true* available qty.
4. Applies the `available_stock` derived view defined in `context.yaml`.

The agent never sees any of that. If a different company's ERP scattered the
same information differently, only the discovery output and adapter would
change — the agent and tool surface stay identical.

### Live learning

Three pattern families are mined from `WORKFLOW_OBS` and re-derived from
scratch every learning cycle (so corrections via feedback take effect):

| Kind         | Example                                                                 |
|--------------|-------------------------------------------------------------------------|
| `ROUTING`    | "Fragile items source from WH02" (84% confidence over 37 observations) |
| `APPROVAL`   | "Vendor V1001 invoices ≤$4,260 are auto-approved by u_mgr_c"           |
| `PREFERENCE` | Free-text human feedback distilled per tool                            |

Patterns require ≥5 observations and ≥60% confidence to be codified. The
adapter consults them at decision time:

- `suggest_source_warehouse` checks `ROUTING` patterns and overrides the
  default "highest available stock" heuristic when a learned preference
  applies.
- `post_invoice` checks `APPROVAL` patterns to fast-track invoices that
  match a learned vendor + amount-bucket pattern.

The learner runs:
- on every Nth observation (default 10) — keeps it cheap during normal use,
- immediately on any `FEEDBACK` observation — so corrections are felt right away,
- on demand via `python -m learner.miner`.

## Demo scenarios

`python run.py` walks through three:

**Scenario 1 — Inventory restock.** *"We're low on SKU-441 at WH01. Move 80
units from the best source."* The agent calls `get_stock` → `suggest_source_warehouse`
→ `move_stock`. The suggestion's `reason` field cites the learned routing pattern.

**Scenario 2 — Invoice posting.** *"Post a $2,500 invoice from V1001 and another
from V1002."* V1001 auto-posts thanks to the learned vendor fast-track;
V1002 parks for manual approval — same dollar amount, different outcome.

**Scenario 3 — Live correction.** A user submits feedback on a routing
decision. The learner immediately re-mines, the new `PREFERENCE` pattern
appears in `LEARNED_PATTERNS`, and is consulted on the next call.

Run `python run.py inspect` after the demo to see the full pattern table and
recent observation log.

## Running as a real MCP server

The same adapter is exposed over MCP for real client integration:

```bash
python -m mcp_server.server     # speaks MCP over stdio
```

Add to a Claude Desktop or Claude Code MCP config:

```json
{
  "mcpServers": {
    "erp-adapter": {
      "command": "python",
      "args": ["-m", "mcp_server.server"],
      "cwd": "C:/Users/s_cha/OneDrive/Documents/MVP/erp_adapter"
    }
  }
}
```
